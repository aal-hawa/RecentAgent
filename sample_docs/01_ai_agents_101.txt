AI Agents 101

An AI agent is a software system that uses a large language model (LLM) as its reasoning core and can take actions in an environment to reach a goal. Unlike a plain chatbot, which only generates a single response to a prompt, an agent operates in a loop: it observes, thinks, decides on an action, executes that action with a tool, observes the result, and repeats until the task is complete. This simple loop, combined with good tool design, is what turns a language model from a text generator into a system that can actually do things.

The anatomy of a modern agent has four building blocks. First, the LLM core performs reasoning, planning, and decision making. Second, the tools are functions the model is allowed to call, such as searching documents, querying a database, calling an external API, running a calculator, or browsing the web. Third, memory preserves context across steps and sessions: short-term memory is usually the conversation history itself, while long-term memory is often a vector database that stores past knowledge for retrieval. Fourth, the orchestration loop implements the control flow, enforces limits such as a maximum number of tool rounds, and handles errors gracefully.

The most influential agent design pattern is ReAct, short for Reasoning and Acting, introduced by Yao and colleagues in 2022. In ReAct the model emits an explicit Thought explaining what it knows and what it still needs, then an Action naming a tool, then an Action Input for that tool. The system executes the tool and returns an Observation. The model reads the observation and repeats. When it believes it has enough information it produces a Final Answer. The pattern is popular for three reasons: it works with every language model regardless of native function-calling support, it is fully inspectable because every reasoning step is visible in plain text, and it is easy to debug because a failure can be traced to a specific Thought or Observation.

Tool design matters as much as model quality. A good tool has a clear name, a precise description of when to use it, and a single well-defined input. Tools should never raise unhandled exceptions; instead they return an error message as text so the agent can read the failure, adapt, and try a different approach. This mirrors how a human operator deals with a misbehaving command: read the error, adjust, retry. Security is also part of tool design. For example, a calculator tool must never call the language model's output through eval, because a prompt injection could execute arbitrary code; a safe implementation parses the expression into an abstract syntax tree and evaluates only whitelisted operations.

Retrieval-Augmented Generation, or RAG, is the tool that connects an agent to private or fresh knowledge. Instead of fine-tuning a model on documents, RAG retrieves the relevant passages at question time and injects them into the prompt. This keeps knowledge up to date, reduces hallucination by grounding answers in real text, enables citations so users can verify claims, and respects data boundaries because documents stay in the retriever rather than inside the model weights.

Agents also have known limitations. They can loop if the task is ill-defined, which is why production systems impose an iteration budget and a forced final answer. They can be overconfident, which is why answers that use retrieved documents should cite their sources. They can be slow and costly when they call many tools, which is why observation truncation and history bounding are standard optimizations. Finally, they inherit the biases of their underlying model, which is why human oversight and evaluation remain essential in any serious deployment.
