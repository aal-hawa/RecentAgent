RAG Explained: Retrieval-Augmented Generation

Retrieval-Augmented Generation is an architecture that improves language model answers by first retrieving relevant text from an external knowledge source and then asking the model to answer using that text as context. The name describes the two halves: retrieval fetches evidence, augmented generation writes the answer grounded in that evidence.

Why RAG exists. Large language models know only what was in their training data, which creates three chronic problems: knowledge cutoff, meaning the model cannot know recent events; hallucination, meaning the model may confidently invent plausible-sounding facts; and private data blindness, meaning the model has never seen your company manuals, policies, or notes. Fine-tuning can inject some knowledge but is expensive, slow to update, and still prone to hallucination. RAG solves all three problems with one mechanism: at question time, find the right documents and put them in front of the model. Answers become verifiable because the system can show exactly which passages were used.

The standard RAG pipeline has six stages. Ingestion collects raw documents such as PDFs, text files, or web pages and extracts their plain text. Chunking splits the text into passages, typically a few hundred to a thousand characters, ideally with some overlap between consecutive chunks so that an idea split across a boundary is still captured whole. Embedding converts each chunk into a numeric vector using an embedding model such that semantically similar texts land close together in vector space. Indexing stores those vectors for fast lookup; production systems use vector databases, while small systems can use a plain matrix and cosine similarity. Retrieval embeds the user's question and returns the top-k most similar chunks. Generation inserts the retrieved passages into the prompt and asks the model to answer, citing the sources.

Chunking is the stage with the most practical trade-offs. Chunks that are too small lose context, so a passage about a multi-step process may arrive without its steps. Chunks that are too large dilute relevance, because a thousand-word chunk matches many questions while burying the specific sentence that matters. Overlap between chunks, usually ten to twenty percent, preserves continuity. Simple implementations split by characters or words; more advanced ones split on sentence or paragraph boundaries, or use a small model to propose topic-aware breakpoints.

Embeddings and similarity search are the mathematical heart of retrieval. An embedding model maps text to a vector of fixed dimension; with a good model, the cosine similarity between a question vector and a chunk vector approximates their semantic relatedness. Two retrieval backends are common. Neural retrieval uses such embedding models and excels at paraphrase and meaning. Lexical retrieval, such as TF-IDF or BM25, matches exact terms and needs no model download, no network, and no GPU. Hybrid systems combine both and often add a reranker that scores the top candidates with a cross-encoder for maximum precision.

Citations and grounding are what make RAG trustworthy in production. Every answer built from retrieved passages should reference the source document and, where possible, the exact chunk, so a reviewer can click through and verify. If retrieval finds nothing relevant, the system should say so instead of answering from memory. This pattern, retrieval or abstain, is one of the most effective defenses against hallucination.

Finally, RAG systems are evaluated on both halves separately: retrieval quality, usually measured by whether the gold passage appears in the top-k results, and generation quality, measured by faithfulness to the retrieved context and relevance to the question. Common failure modes include poor chunking, embedding models mismatched to the domain language, and prompts that let the model ignore the provided context.
